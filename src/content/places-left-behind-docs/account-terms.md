> **Future Draft.** Places Left Behind is intended to be single-player with local saves. No account, login, or profile exists, and none is promised. This draft prepares terms in case accounts are introduced.

---

## 1. Purpose

Accounts would only be needed for features that require identifying a user across sessions or devices — cloud saves, online services, or community functions.

If accounts are never introduced, this document stays unused.

## 2. When Accounts Would Be Needed

| Feature | Needs an account? |
| --- | --- |
| Local single-player play | No |
| Local saves | No |
| Cloud saves | Yes |
| Online multiplayer | Yes |
| Community submissions | Possibly |
| Purchasing the game | Handled by the storefront, not by a game account |

The default design assumption is that **no account is required to play**. Any feature that requires one should be optional, and the game should remain playable offline without it.

## 3. Registration

1. A user would provide a display name and an email address, or use a supported sign-in provider.
2. Information provided must be accurate and kept current.
3. One account per person. Duplicate accounts may be closed.
4. The studio may refuse a registration that appears fraudulent or abusive.
5. Usernames that impersonate another person, the studio, or a public figure may be refused or changed.

## 4. Age and Guardian Consent

1. A minimum age would be set before accounts were introduced.
2. Where a user is below the age of digital consent in their jurisdiction, guardian consent would be required.
3. The studio would not knowingly collect personal data from a child without the consent the law requires.
4. Because the studio's own operator is currently under 18, the policy for minors should be reviewed with that in mind.

## 5. Account Security

1. The user is responsible for keeping their credentials confidential.
2. The studio would never ask for a password by email or message.
3. Suspicious activity should be reported to the studio.
4. The studio may suspend an account that appears compromised, and would work with the holder to restore it.
5. Passwords would be stored only in hashed form, using an appropriate algorithm, if the studio operates its own authentication.

## 6. Acceptable Use

An account holder would not be permitted to:

1. share, sell, or transfer an account;
2. use another person's account without permission;
3. attempt to access accounts or data that are not theirs;
4. use the account for harassment, fraud, or infringement;
5. evade a suspension;
6. automate access in a way that burdens the service;
7. upload malicious content through any account feature.

## 7. Data Held About an Account

Minimum expected data:

| Data | Purpose |
| --- | --- |
| Display name | Identification to the user and, where relevant, to other users |
| Email address | Sign-in, recovery, and essential notices |
| Hashed password or provider identifier | Authentication |
| Account creation date | Administration |
| Linked game progress, if cloud saves exist | Providing the feature |
| Moderation history | Safety and enforcement |

The account would not be used to build an advertising profile, and data would not be sold. Full detail would be in an updated privacy policy, published before accounts launch.

## 8. Deletion and Portability

1. A user could request deletion of their account and associated data.
2. Deletion would remove personal data, except where retention is required by law or needed to resolve an open dispute.
3. Where the law provides a right to data portability, the studio would provide the user's data in a usable form.
4. Deleting an account may remove access to cloud saves and to content tied to it. That consequence would be stated before deletion.

## 9. Suspension and Closure

1. The studio may suspend or close an account for a breach of these terms, or where required by law.
2. Where practical, the user would be told why and given a route to appeal.
3. Closure does not entitle the user to a refund, except where the law or the store's policy requires one.
4. The user may close their own account at any time.

## 10. Purchases and Entitlements

1. Purchases would be handled by a storefront, not by the studio's account system.
2. An account would not be a store of monetary value, and account balances are not planned.
3. If virtual items were ever introduced, their terms would need separate, clear disclosure — including what happens to them on closure.

## 11. Termination of the Service

If accounts were discontinued:

1. the studio would give reasonable notice;
2. users would be told how to export or preserve what they can;
3. local play would remain available if it does not depend on accounts;
4. data would be deleted in line with the retention policy.

## 12. Disclaimers

Accounts and any associated service would be provided "as is", without warranty, to the maximum extent permitted by law. Service interruptions, data loss, and feature changes are foreseeable and would be disclosed.

## 13. Legal Review Requirements

1. Data protection obligations for account data, including for minors.
2. The minimum age, and whether age verification is proportionate.
3. Consumer law obligations for any paid feature tied to an account.
4. Cross-border data transfer, if a provider outside the user's country is used.
5. Deletion and portability obligations in the relevant jurisdictions.
6. Confirmation of the intended jurisdiction, Georgia, United States.
7. Capacity and guardian involvement, given the owner is currently under 18.

## 14. Open Items

1. Whether accounts will exist at all.
2. Whether sign-in would be first-party or through a provider.
3. Whether cloud saves would require an account.
4. Whether community features would share the same account.
5. What the minimum age would be.
